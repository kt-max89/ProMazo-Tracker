We need to implement a human-in-the-loop task proposal flow in our internal Next.js app, using Option B: a single response with an optional structured proposal sidecar.

Current context:
- We already have a chat orchestration flow
- It uses a tight one-tool maximum pattern per user prompt
- The flow is:

  1. user sends prompt
  2. agent does normal one-tool max flow
  3. final answer is built
  4. optionally detect proposed tasks
  5. stream assistant text
  6. stream task_proposal event if proposal exists
  7. stop

- We already have a hook point in ChatOrchestration for future proposed task actions
- All task writes must go through taskService.ts
- No direct DB access from chat
- No autonomous execution
- User approval is required before any task creation

Decision:
We are explicitly choosing Option B, not a separate structured LLM pass.

That means:
- the same model response that generates the assistant answer may also include an optional structured proposal sidecar
- we do NOT want a second LLM call just to generate task proposals
- we want low latency, minimal complexity, and a clean MVP

Goal:
Allow the assistant to optionally propose one or more new tasks in the same turn, then show those proposed tasks in the UI for user approval before creating them.

High level product behavior:
1. Assistant answers the user normally
2. If the assistant also proposes tasks, the backend emits a separate task_proposal SSE event after streaming the assistant text
3. The frontend shows a popup/modal with the proposed tasks
4. The user can choose:
   - Not Yet
   - Create Tasks
5. If the user chooses Create Tasks:
   - create all approved tasks through taskService.ts
   - force status = not_started
6. If the user chooses Not Yet:
   - do not create anything
   - close the popup
   - append a follow-up assistant-style message asking what should be refined

Important constraints:
- Keep this simple
- This is a single internal Next.js app
- No MCP changes needed here
- No second LLM pass
- No autonomous writes
- No direct DB access from chat
- No overengineering
- Validate all proposal data before showing it in UI or writing anything
- Only emit a proposal if it passes validation well enough for an MVP

- when tasks are ultimately created, force status = not_started
- do not allow proposal payload to directly set any other status

If the proposal is malformed or empty after validation:
- do not emit task_proposal
