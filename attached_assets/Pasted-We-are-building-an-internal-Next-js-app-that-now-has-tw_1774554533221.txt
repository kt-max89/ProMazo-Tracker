We are building an internal Next.js app that now has two different knowledge sources:

1. Document RAG
   - standup logs
   - notes
   - goals documents

2. Task system
   - task tracker backed by a database
   - tasks have statuses and archive state

I need you to add a simple orchestration layer for chat so the assistant can use the right source at the right time without overengineering anything.

Important constraints:
- Keep this simple
- Single internal app only
- No MCP
- No autonomous agent behavior
- No overengineering
- The future plan is that chat may help create, update, move, and edit tasks, but always with explicit user input/approval
- For now, focus on routing, retrieval, and clean architecture
- This is Next.js, so use existing app patterns and keep mutations server-side

Core problem to solve:
When a user chats, sometimes they are asking about:
- tasks in the task tracker
- documents in the RAG system
- both tasks and documents
- neither, and the model can answer directly

We do NOT want to always send both task data and document context into every prompt.
We need a lightweight orchestration layer that decides when to query:
- tasks only
- docs only
- both
- neither

Design direction:
Add a new server-side orchestration layer for chat.

Suggested naming:
- chatOrchestrator
- retrievalRouter
- promptBuilder

Use whichever names fit the existing codebase best, but keep responsibilities clear and minimal.

What I want built:

1. Add a routing layer before retrieval
Create a simple message router that classifies each user message into one of these routes:
- TASKS_ONLY
- DOCS_ONLY
- BOTH
- NEITHER

This should happen before any retrieval is run.

Start simple:
- use rules first
- only use an LLM classification step if the request is unclear and if that is easy within the current architecture
- if rules are sufficient for MVP, that is preferred

Examples of likely task queries:
- what is blocked
- what is in progress
- what tasks do we have
- what is open
- move this task
- mark this done
- archive this
- create a task

Examples of likely doc queries:
- what did the standup notes say
- summarize the goals document
- what was mentioned in the notes
- based on the logs
- retrieve the standup context

Examples of likely BOTH queries:
- which goals from this week are not represented in tasks
- compare the standup notes to the task board
- which blockers in the notes are not tracked in tasks

Examples of NEITHER:
- conversational/help questions that do not require retrieval

2. Add compact task retrieval for LLM use
Do NOT send the full task board into every prompt.
Do NOT dump raw task rows unless the result set is very small.

Instead, add task retrieval helpers that return compact relevant task context for the current message.

Please create or extend task service methods like:
- getTaskCounts()
- getTasksByStatus(status)
- searchTasks(query)
- getCompactTaskContext(filters)

The returned task context should be concise and structured.
For example:
- counts by status
- only the matching or most relevant tasks
- only fields needed for reasoning

Use task DB as the source of truth for current operational state.
Do not infer task state from documents if task DB already has the answer.

3. Add document retrieval only when needed
Do NOT run document RAG for every message.
Only call document retrieval if the router says DOCS_ONLY or BOTH.

Use the existing RAG/document retrieval logic if present.
If there is already a retrieval service, reuse it.
If not, add the thinnest possible wrapper around current retrieval code.

Document retrieval output for the LLM should also be compact:
- top relevant chunks only
- source info if available
- avoid sending huge logs or large raw documents

4. Add a chat orchestrator
Create a server-side orchestration function that handles a chat message roughly like this:

- inspect the message
- decide route: TASKS_ONLY / DOCS_ONLY / BOTH / NEITHER
- fetch only the needed context
- build the final prompt with only the needed context sections
- call the main LLM
- return the answer

Keep this straightforward and readable.

Pseudocode shape is fine to follow:

handleChatMessage(message, conversationState):
  route = routeMessage(message, conversationState)

  if route needs tasks:
    taskContext = getCompactTaskContext(...)

  if route needs docs:
    docContext = retrieveRelevantDocumentContext(...)

  prompt = buildPrompt({
    message,
    conversationState,
    taskContext,
    docContext
  })

  answer = callLLM(prompt)
  return answer

5. Add a prompt builder
Create a simple prompt builder that can include these sections only when present:
- system instructions
- conversation context
- task context
- document context
- user message

Important prompt rules:
- if task context is present, use it for task and board questions
- if document context is present, use it for document questions
- do not invent facts not present in the supplied context
- if both are present, the model may compare them
- keep prompts compact

6. Preserve future support for task actions, but do not execute automatically
We know that later chat may create or update tasks, but only with user approval.

For now, structure the orchestration layer so that it can later support proposed task actions.
Do NOT fully implement autonomous task mutation right now.

If easy, add a clean place in the architecture for future structured action proposals, such as:
- create_task proposal
- update_task_status proposal
- archive_task proposal

But do not actually wire autonomous writes into chat in this step unless the existing app already has a clear confirmation pattern.

The task DB writes should continue to go through the shared server-side task service only.

7. Keep architecture minimal
Please do NOT add:
- MCP
- drag and drop
- autonomous agents
- extra event buses
- background jobs
- vector retrieval for tasks
- complex multi-step planners
- unnecessary abstraction layers
- separate microservices

This is a single internal Next.js app.
We want a clean, simple internal orchestration layer.

Implementation principles:
- inspect existing Next.js structure first
- reuse current app patterns
- prefer fewer files over too many abstractions
- keep business logic server-side
- keep client components only for UI interactivity
- make the smallest reasonable assumptions and proceed

Suggested modules, if helpful:
- taskService.ts
- documentRetrievalService.ts
- routeMessage.ts
- chatOrchestrator.ts
- promptBuilder.ts

If the codebase already has better naming or structure, reuse that instead of forcing new abstractions.

Deliverables:
1. routing layer for deciding TASKS_ONLY / DOCS_ONLY / BOTH / NEITHER
2. compact task-context retrieval helpers
3. document retrieval integration that only runs when needed
4. chat orchestrator that fetches only required context
5. prompt builder with optional task/doc sections
6. integration into the separate chat interface
7. short summary of what was added and any assumptions made

Important decision rules:
- operational board questions should prefer task DB, not document RAG
- source-content questions should prefer document RAG
- comparison questions can use both
- retrieval should be on-demand, never automatic by default for every message

Optimize for a working internal MVP, not perfect architecture.
Please implement this end to end.
