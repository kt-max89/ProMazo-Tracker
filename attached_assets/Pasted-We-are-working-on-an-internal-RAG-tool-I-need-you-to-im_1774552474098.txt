We are working on an internal RAG tool. I need you to implement a new feature in our existing Next.js app.

High level goal:
Create a new section that includes:
1. a separate chat interface
2. a task tracker UI with Notion-like tiles/cards
3. a simple backend-backed task system

Important constraints:
- Keep this simple
- Do not overengineer
- This is a single internal app
- Do NOT add MCP
- Do NOT build a complex agent framework yet
- The later plan is that the chat interface may become an agent that can create, update, move, and edit tasks, but always with user input/approval
- For now, just build the foundations cleanly so that later we can wire chat actions into the same task service

Technical direction:
- This is Next.js, not a separate React frontend + separate backend app
- Use the existing app patterns where possible
- Prefer simple Next.js route handlers or server actions
- Create one shared server-side task service for business logic
- All task reads/writes should go through that service
- Do not let business logic get duplicated across UI and backend
- Do not create direct browser-to-database task writes
- Use soft archive behavior, not hard delete, unless the codebase already has a clear delete pattern we should follow

Core product requirements:
We need a new tab/window/page for a task tracker.
It should feel somewhat like Notion, with tiles/cards.
Users should be able to create tasks in the UI.
Each task can be in one of 4 statuses:
- not_started
- in_progress
- blocked
- done

Use those exact internal values in code, and map them to display labels:
- Not started
- In progress
- Blocked
- Done

We originally discussed separate tables for open and archived tasks, but do NOT do that.
Instead:
- create one tasks table
- use an is_archived boolean
- open tasks are is_archived = false
- archived tasks are is_archived = true

What I want you to build:

1. Database schema
Create a simple tasks table with only the fields needed for MVP:
- id
- title
- description
- status
- blocked_reason
- is_archived
- created_at
- updated_at

Optional but nice if easy:
- created_by
- archived_at

Rules:
- title is required
- status must be one of: not_started, in_progress, blocked, done
- blocked_reason should be nullable, but if a task is moved to blocked, validate that blocked_reason is present
- use soft archive, not separate archive table

2. Shared server-side task service
Create a single task service module that handles:
- listTasks(filters)
- createTask(input)
- updateTask(id, input)
- archiveTask(id)
- restoreTask(id)

This service should contain the validation/business rules.
UI and route handlers should call this service.
Keep it straightforward and readable.

3. API / server interface
Because this is Next.js, use whichever pattern fits the current codebase best:
- route handlers under app/api/...
or
- server actions if that is already the project pattern

Either way, all writes must go through the shared task service.

We need support for:
- listing open tasks
- listing archived tasks
- creating a task
- editing a task
- changing status
- archiving a task
- restoring a task

4. Task tracker UI
Create a new page/tab/section for Task Tracker.

UI expectations:
- simple and clean
- not flashy
- internal tool quality is fine
- cards/tiles grouped by status
- four columns or sections:
  - Not started
  - In progress
  - Blocked
  - Done

Each task card should show:
- title
- short description if present
- status badge or clear label
- blocked indicator if relevant

At the top of the page include:
- button to create new task
- toggle or tabs for Open vs Archived
- basic search/filter only if easy, otherwise skip for now

Clicking a task should open a simple edit modal, drawer, or detail panel.
Do not spend too much time on advanced UX.
Basic usable CRUD is more important than polish.

5. Create task flow
Users must be able to create a task from the task tracker UI.
Minimum fields:
- title
- description
- status

If status is blocked, require blocked_reason.

6. Archive behavior
Do not delete tasks from the database.
Archive means:
- set is_archived = true
Optionally:
- set archived_at timestamp if we add that field

Archived tasks should appear in a separate Archived view.
Users should also be able to restore archived tasks.

7. Separate chat interface
Add a separate chat interface page/section for now.
Keep it simple.
This does NOT need full agent behavior yet.

For now:
- create the basic UI shell
- simple message list area
- input box
- send button
- can be stubbed or wired to existing chat logic if present

Important:
The chat and task tracker are separate interfaces for now.
Do not overconnect them yet.

However, structure the code so that later we can have the chat trigger task operations through the same shared task service.
That means task logic should remain isolated in the server-side task service.

Implementation principles:
- Keep code minimal
- Prefer fewer files over too many abstractions
- Follow existing project conventions
- Do not introduce unnecessary libraries unless the project already uses them
- Do not build drag-and-drop yet unless it is already trivial in the stack
- Do not build notifications, comments, tagging, assignment, or analytics yet
- Do not build autonomous task changes by AI
- Assume any future chat-driven task changes will always require user input/confirmation

Deliverables:
1. database schema/migration changes
2. task service
3. route handlers or server actions
4. task tracker page
5. create/edit/archive/restore task flow
6. separate chat page/shell
7. short summary of what was added and any assumptions made

Before coding:
- inspect the existing Next.js app structure
- reuse its patterns for data access, styling, forms, and API handling
- if something in the stack is unclear, make the smallest reasonable assumption and proceed
- do not stop to redesign the whole system

Please implement the MVP end to end.
