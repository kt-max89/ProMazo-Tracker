We need to refactor the current chat orchestration in our internal Next.js app to a very tight tool-based pattern.

Current context:
- This is a single internal app
- We have two main knowledge sources:
  1. task database / task tracker
  2. document RAG for standup logs, notes, and goals docs
- The current orchestration/routing approach is only okay and misses the mark too often
- We now want to move to a minimal tool-based agent pattern
- Do NOT overengineer this
- Do NOT build a broad autonomous agent system
- Do NOT add MCP complexity beyond what is needed for this tight tool call setup

Goal:
Build a very constrained tool-use flow for chat where the model can decide whether to use:
- see_tasks
- read_docs
- or no tool

Key constraints:
- Maximum of ONE tool call per user prompt
- No multi-step looping
- No repeated tool retries inside the same turn
- No autonomous task writes
- No tool call chains
- If retrieval is weak or empty, the assistant should still answer and explicitly say something like:
  "I didn't find anything useful. Should we try again with a different approach?"
- Optimize for low latency and predictable behavior

Architecture direction:
This is a Next.js app.
Keep it simple and server-side.
We want a tight pattern like:

1. User sends message
2. Model decides intent:
   - use see_tasks
   - use read_docs
   - use no tool
3. If a tool is selected, call exactly one tool once
4. Pass the tool result back to the model
5. Model writes final response
6. End turn

We do NOT want:
- agent loops
- more than one tool call
- background planning
- retries within the same turn
- separate orchestration microservices
- broad abstractions

Important product behavior:
- If the model chooses a tool and the result is limited, weak, or empty, it should still respond usefully
- It should not silently fail
- It should say that it did not find enough and suggest trying again differently
- The response should stay grounded in what was actually found

Please implement this as a clean internal MVP.

What I want built:

1. Replace current brittle routing with a tight tool-intent pattern
We need a model-controlled intent decision that chooses one of:
- SEE_TASKS
- READ_DOCS
- NO_TOOL

There should be no BOTH option in the same turn for now.
One user prompt gets at most one tool call.

Intent decision should happen first.
Then either:
- call one tool once
- or skip tools and answer directly

You can implement this as:
- a structured intent selection step
- or a tool-capable model call with strict limits
Choose the simplest reliable implementation for the current stack.

Important:
If using the model for intent selection, make the output structured and easy to validate.
For example:
- intent
- optional tool arguments
- confidence or reason if useful

2. Implement exactly two read-only tools
We only want these two tools for now:

A. see_tasks
Purpose:
- inspect the task tracker / task DB for current operational state

This tool should support targeted lookup and compact outputs.
Do NOT dump the entire task board.

Suggested inputs:
- query: string | optional
- status: one of not_started, in_progress, blocked, done | optional
- includeArchived: boolean, default false
- limit: number, default small
- mode: "summary" | "matching_tasks"

Suggested behavior:
- return concise structured task context
- include counts by status when useful
- include only relevant tasks
- include only fields needed for reasoning, such as:
  - id
  - title
  - status
  - description snippet
  - blocked_reason if relevant

Suggested outputs:
- summary counts
- matching tasks
- indication if nothing useful was found

Use task DB as source of truth for operational/task status.

B. read_docs
Purpose:
- retrieve relevant context from standup logs, notes, and goals documents

Suggested inputs:
- query: string
- docType: optional enum or filter if easy, such as standup, notes, goals
- limit: small default like 3 to 5

Suggested behavior:
- run existing document retrieval / RAG only when this tool is chosen
- return a compact set of relevant chunks
- include source metadata if available
- do not return large raw documents or too many chunks

Suggested outputs:
- top relevant chunks
- source names / timestamps if available
- indication if nothing useful was found

3. Add a strict one-tool-call orchestration flow
Please implement a chat handling flow like this:

A. Receive user message
B. Decide intent: SEE_TASKS / READ_DOCS / NO_TOOL
C. If SEE_TASKS or READ_DOCS:
   - call that tool exactly once
D. Build final answer prompt with:
   - conversation context if needed
   - user message
   - tool result if present
E. Generate final assistant response
F. End

Hard rules:
- only one tool call maximum per user prompt
- do not call both tools
- do not do a second attempt in the same turn
- do not auto-fallback from one tool to the other in the same turn
- do not create an open-ended loop

4. Design graceful failure behavior
If the chosen tool returns weak, sparse, or empty results:
- the assistant should still respond
- it should say that it did not find enough
- it should suggest trying again with a different approach

Examples of desired behavior:
- "I checked the task board but did not find a clear match. Should we try again with a different keyword or status?"
- "I searched the documents but did not find anything useful for that phrasing. Should we try again with a different approach?"
- "I did not find enough to answer confidently from the available context. Should we try a narrower or broader search?"

This fallback behavior is important.

5. Keep tool outputs compact and structured
This is critical for latency and quality.

For see_tasks:
- compact summary or matching tasks only
- small limits
- avoid huge payloads

For read_docs:
- small top-k only
- concise chunk text
- include source info if present
- avoid massive context dumps

6. Integrate into the existing separate chat interface
Hook this new tool-based chat flow into the current chat interface/page.
Reuse existing chat UI patterns if they already exist.
Do not redesign the UI unless needed.
Focus on backend behavior and correct responses.

7. Keep future extensibility without implementing it now
We may later support task-changing actions through chat, but always with user approval.
Do NOT implement write tools now.
